# Meeting Notes — Controllers & Secrets Alignment
**Date:** 2026-06-02
**Attendees:** Ibrahim Takouna, Pierre-Yves Aillet, Guillaume Audic, Boris Behrens, Zafar Akhtar + others

---

## Why this meeting
Align on secrets handling and security across controllers — overlap between CB and OS teams needed a shared session.

---

## Decisions made

### Keystone
- **Dedicated Keystone per service confirmed.** Object Storage gets its own Keystone — no need for the shared OPCP Keystone operator. → Closes OSQ-02 direction (dedicated path confirmed).
- Keystone operator can be reused with unused controllers disabled via feature flag.
- Federation config stays in the **data plane** of the service.
- RADOS gateway still needs to federate against Keycloak — **open work**.

### Secrets & credentials
- OpenStack credentials for the operator already exist as a secret in the OCP namespace ✅
- Keycloak L3 client ID and secret: generated by cluster API on account creation, passed as Terraform variables to the data plane. Same pattern as VM & Block. → Partially closes OSQ-17.

### L2 / L3
- L2 has no visibility into L3.
- L3 can make API calls back to L2 via Terraform providers if needed.
- Enabler services notification pattern (L3 → L2, e.g. Grafana notified on new account) — **not yet solved**.

### RBAC for provisioner pod
- Permissions live in the **service repo as raw manifests**, not hardcoded in the Helm chart.
- It's the **Kubernetes provider inside the Terraform module** that needs the permissions — not the pod itself. Confirmed, no objections.

---

## Questions raised by Zafar

**1. Grafana / Observability — L2 awareness of new L3 accounts**
When deploying a shared service in the control plane (e.g. Grafana), how does L2 know when a new account/realm is created on L3 so it can update its config?
- Pierre: data plane Terraform can call back to L2 via provider.
- Not fully solved for enabler services — flagged as future work.

**2. Keystone operator reuse**
Suggested keeping the Keystone operator but disabling unused controllers via feature flag, to avoid reimplementing the same logic across teams.
- Pierre agreed: valid approach, not complicated.
